# Editorial Policy

이 문서는 ascendy-blog의 **편집 정책**이다. 블로그팀 Claude와 Codex 모두
이 문서를 binding으로 따른다. 정책 위반은 곧 머지 차단 사유.

## 왜 쓰는가 — 3대 목적

이 블로그는 글 자체의 유명세나 기술 과시가 목적이 **아니다.** 세 가지를
위해 쓴다:

1. **신뢰성 입증** — Ascendy가 기술적으로 믿을 만하다는 것을, 말이 아니라
   실제 결정·트레이드오프·문제 해결로 보여준다.
2. **서비스 홍보** — Ascendy라는 서비스를 알린다. 단 홍보는 #1로 한다 —
   "우리가 최고"가 아니라 "이 문제를 이렇게 풀었다"가 곧 홍보다. 톤 규칙
   "자뻑 금지"는 그대로 유지된다. 신뢰는 자랑이 아니라 substance에서 나온다.
3. **기술 기록** — 결정의 맥락을 남겨, 6개월 뒤 "왜 B를 골랐나"의 답이
   휘발되지 않게 한다.

세 목적이 충돌하면 **#1(신뢰성)을 우선**한다 — 신뢰를 잃는 홍보는 역효과다.

## 누구를 위해 쓰는가

1. **인간 개발자** — 외부 엔지니어가 검색하다 도착하거나, 우리 팀의
   결정 기록을 참고하러 오는 사람.
2. **AI 에이전트** — Perplexity, ChatGPT, Claude, Gemini, 검색엔진.
   인용 단위로 잘 잘리고, 구조화 데이터로 신뢰성을 입증해야 함.

순서가 곧 우선순위, 그러나 **택일이 아니라 둘 다**다 — 사람이 읽기 좋은
글이 AI도 잘 인용한다. 사람이 못 읽는 글은 AI도 못 인용한다.

## 글감은 어디서 오나 (3종)

1. **3팀 인테이크** — backend/frontend/infra가 private repo에 떨군 글감.
   `sourceIntake` 필수(정제본 경로). 자세한 흐름은 "인테이크의 공개 경계".
2. **메타** — 블로그 자체 안내·회고. `sourceIntake` 면제.
3. **사용자 직접 지정** — 사용자가 채팅/문서로 주제·자료를 직접 준다.
   `sourceIntake` 면제(사용자가 곧 소스). 기록이 필요하면 `docs/intake/from-user/`에
   redaction 후 보관. 주로 제품·발표·공지 성격(목적 #2 홍보)에 쓰인다.

**어떤 소스든 redaction 체크리스트는 동일하게 통과**해야 한다. 입구가 다를
뿐, 공개 가드는 같다.

## 톤

- 한국어 기본. 영어가 더 정확한 용어/고유명사는 영어 유지.
- 1인칭 복수 "우리". 단정과 추측을 분리하라 ("결정했다" vs "현재는 …로 보인다").
- 자뻑 금지. 실패와 트레이드오프를 같이 쓴다. "Ascendy는 최고다" 같은
  문장은 AI 인용 가치를 떨어뜨린다 — 사실과 측정값을 적어라.

## 길이

- TL;DR 3~5줄 (AI 인용 단위).
- 본문 700~2,500자 (긴 글은 시리즈로 쪼개라).
- 코드 블록은 self-contained하게, 50줄 이상은 GitHub 링크.

## 구조 — 모든 글이 가져야 할 골격

1. TL;DR
2. 배경 (왜 이 글인가)
3. 본문 (결정/변경/패턴)
4. 결정/트레이드오프 (특히 infra)
5. 후속 / 측정 / 관련 글

`_template.md`가 이 골격을 강제한다.

> **후속 섹션 — post-약속과 work-next-step을 구분한다.** "후속"에는 두 종류가
> 섞일 수 있다: (a) 해당 팀의 엔지니어링 다음 단계(예: "Phase 2 삭제", "CI로
> 강제")와 (b) 미래 게시물 약속(예: "2부에서 다룬다"). (a)는 블로그의 채무가
> 아니다 — 팀이 자기 일정에 일하고 글감 가치가 생기면 인테이크를 떨군다. (b)는
> 옮기는 순간 **공개된 편집상 약속**이 되므로, 떠도는 "2부 coming"을 막기 위해
> 출처별로 추적한다: **팀 인테이크 소스**면 해당 팀에 `from-blog` 후속 인테이크
> 요청으로(Cross-repo 워크플로 참조), **사용자 직접 지정 소스**면 사용자가 후속
> 글감을 제공하는 채널이므로 별도 from-blog 요청 없이 사용자가 채널이 된다.
> 약속의 substance는 반드시 인테이크/운영자·사용자 언급에 근거해야 하며, 블로그가
> 미래 글을 무에서 약속하지 않는다.

## 메타데이터 (frontmatter)

`src/content.config.ts`의 스키마가 강제. 누락 시 빌드 실패.

- `title`, `description`, `pubDate`, `tags`, `category` 필수
- `sourceIntake` — 3팀 산출물 기반 글이면 필수
- `draft: true`, `redactionReviewed: false`로 PR을 열고, 머지 직전에 반대로

리뷰 + 사람 머지.

## AO (GEO/AEO) — AI가 인용하게 쓴다

SEO(검색 노출)에 더해, 생성형 엔진(ChatGPT·Perplexity·Gemini 등)이 우리 글을
**신뢰 출처로 인용**하게 만드는 것을 의식한다. SEO·AEO·GEO는 택일이 아니라
3층 보완 — SEO가 기반, AEO가 답변 추출, GEO가 인용 신뢰. 검증된 인용 유도
요인을 콘텐츠에 반영한다:

- **귀속된 근거** — 주장에 출처를 붙인다(공개 문서·표준·우리 공개 PR 링크).
  "~라고 한다"보다 "[X]에 따르면 ~"가 인용된다.
- **구체 수치·측정값** — "빨라졌다"가 아니라 "p95 320ms→110ms"처럼. 단
  redaction을 통과한, 공개 가능한 수치만.
- **질문형 헤딩 + 간결한 답** — 헤딩을 독자가 검색할 법한 질문으로 쓰고,
  바로 아래 2~4줄로 답한다(AEO: 답변 추출 용이).
- **self-contained 단락** — 잘려 나가도 의미가 서는 문단(구조 규칙과 동일).
- **기술 계층** — robots.txt가 AI 크롤러 허용 + JSON-LD + `llms.txt`(예정).

이는 "자뻑 금지"와 충돌하지 않는다 — 수치·출처·정직한 트레이드오프가 곧
인용 가치이자 신뢰성(3대 목적 #1)이다.

## 읽는 맛 — 사람도 끝까지 읽게 쓴다

AO(위)는 글이 *발견·인용*되게 하지만, 그것만으로 인간이 *끝까지 읽는다는*
보장은 없다. 정보 밀도만 높고 텐션이 없으면 에이전트에겐 매력적이어도 사람에겐
심심할 수 있다(아직 측정 전 working hypothesis — engagement 데이터로 검증 대상).
**citability는 유통, 읽는 맛은 도달** — 둘 다 필요하다는 전제로 쓴다.

**계층으로 양립한다.** TL;DR·질문형 헤딩·교훈 박스·결론(스캐너·에이전트용)은
그대로 두고, **본문을 내러티브로** 쓴다. 위는 요약, 아래는 이야기.

본문에 적용할 네 가지:

- **장면화** — "메모리를 튜닝했다"보다 "새벽 3시, OOM이 세 번째 터졌다". 추상
  동사를 구체 장면·숫자·순간으로. **단 그 장면·숫자·순간은 source(인테이크·인터뷰·
  운영 기억)에 실재하고 redaction을 통과한 것만 쓴다 — 드라마를 위해 없는 디테일을
  지어내거나 재구성하는 것은 fabrication이며, 우리 1차-경험·정직 원칙의 정반대다.**
- **텐션/복선** — 문제 → 악화 → 해결의 드라마. 자만의 순간을 복선으로 깔아
  뒤의 추락을 예고한다.
- **목소리** — 중립 위키 톤 대신 사람 냄새. 제목 콜백, 약간의 자조(과용 금지).
- **리듬** — 짧은 문장 반복으로 좌절·긴장을 체감시킨다("부팅하자마자 OOM.
  다시 또 OOM.").

톤 섹션의 '강한 의견·솔직한 실패'가 재미의 핵심 재료다 — 재미는 *미화*가 아니라
**정직한 드라마**다(자뻑 금지와 정합).

**균형 — citability를 해치지 마라.** 내러티브가 과해 핵심 주장이 산문에 묻히면
AO가 죽는다. self-contained 단락·TL;DR·질문형 헤딩은 사수하고, 재미는 **본문
표층에만** 주입한다. **재미는 표현(장면 배치·목소리·리듬)에서 나오지, 없는 사실을
지어내서 나오지 않는다** — 새 디테일을 쓰려면 source-backed + redaction-approved여야
한다. 사실·수치·구조·redaction은 무손상.

> **before/after (style-only — 사실 0 추가).** "OOM이 계속 났다." → "OOM. 다시
> 띄우면 또 OOM." 같은 사실에 리듬만 더했다. 반면 장면·숫자를 *새로* 넣고 싶다면
> (예: '새벽 3시', '세 번째') 그 디테일이 **source에 실재할 때만** 허용된다 —
> 근거가 없으면 넣지 않는다. 인터뷰 하네스(운영자에게 묻기)가 그 디테일을
> source로 끌어올리는 정식 경로다.

## 비공개 → 공개 가드

`docs/redaction-checklist.md`를 PR마다 통과해야 한다. 자세한 항목은 그쪽
참조. 핵심:

- 인증 정보, 토큰, kubeconfig, 사내 호스트명, 클러스터 이름, registry
  path, 사내 IP, 고객/파트너 식별 정보, 미공개 비즈니스 결정 → **금지**.
- 의심스러우면 redaction. "이거 공개해도 되나?"가 떠오르면 답은 No.

### 번역본도 독립 redaction

블로그는 ko/en 다국어를 지원한다(`src/i18n/`, `astro.config.mjs`의 `i18n`).
번역본은 **파생물이지 자동 안전물이 아니다.** 번역 과정에서 원문의 일반화가
풀리거나(예: "프로덕션 클러스터" → 실명으로 되돌림), 한국어 기준 체크리스트가
놓친 표현이 영어로 노출될 수 있다.

- 각 언어판(ko/en)은 `redaction-checklist.md`를 **독립적으로** 통과해야 한다.
  한쪽이 통과했다고 다른 쪽이 자동 통과되지 않는다.
- 번역본의 `redactionReviewed`는 그 언어판을 직접 검수한 결과여야 한다.
- AI로 초벌 번역하더라도, 게시 전 redaction 재확인은 동일 강도로.

**`translationKey` 규칙(hreflang 무결성):** 같은 글의 ko/en 판은 동일한
`translationKey`를 단다. **한 `translationKey`당 한 언어에 정확히 한 글** —
같은 lang에서 key를 중복하면(또는 번역인데 한쪽이 key를 빠뜨리면) hreflang
짝이 깨진다. 스키마가 강제하지 못하므로 리뷰에서 확인한다(중복/누락 금지).

## 인테이크의 공개 경계

`ascendy-blog`는 GitHub public repo이고, 제안 팀 repo(backend / frontend /
infra)는 모두 private다. 이 비대칭을 네 원칙으로 다룬다:

1. **raw 인테이크는 제안 팀의 private repo에만.** 원본 소스는
   `<팀 repo>/docs/blog-intake/`에 쓴다. redaction 전 raw를 블로그 public
   repo에 커밋하지 않는다 — 한 번 push 되면 git history에 남아 사후 삭제로
   정보 회수가 불가능하다.
2. **블로그팀이 유일한 공개 게이트키퍼.** 팀 private repo의 인테이크를
   읽기 전용으로 열람 → `docs/redaction-checklist.md`를 한 항목씩 통과 →
   **정제된 기록만** 블로그 public repo의 `docs/intake/from-<team>/`에
   커밋한다. public에 들어가는 인테이크 기록은 이미 redaction을 거친 것이다.
3. **제안 팀은 민감 항목을 숨기지 말고 표시.** private repo이므로 원본을
   그대로 적되, `docs/intake-template.md`의 "외부에 공유하면 안 되는 부분"에
   무엇이 들어있는지 명시한다 — 블로그팀이 그걸 보고 제거·일반화한다.
4. **사용자의 최종 머지 = 공개.** draft/redactionReviewed 게이트는 포스트에만
   걸리고 인테이크 기록 자체에는 빌드 게이트가 없으므로, 인테이크 기록 PR도
   사람이 추가로 검토해서 머지한다.

요약: public repo에 올라온 인테이크 기록은 "정제 완료된 1차 공개 자료"다.
raw는 절대 public에 닿지 않는다.

## 게시 / 배포

- main 브랜치 머지 = 즉시 배포 (Cloudflare Pages).
- 따라서 **draft는 절대 main에 머지하지 않는다** (별도 preview 브랜치 사용 시 OK).
- 핫픽스 직접 push는 사람만, 명시적 비상시에만.

## 정정 / 철회

- 사실관계 정정: 본문 수정 + `updatedDate` 갱신 + 글 하단에 "정정 노트" 단락.
- 글 전체 철회: 파일 삭제하지 말고 `draft: true`로 복귀 + PR 본문에 사유.
  과거 외부 인용을 깨뜨리지 않기 위한 검토 후 영구 삭제.
