> **정제 노트.** 원본이 표시한 대로 **구체 건수는 실제 사용자 라이브러리 규모라
> 예시 숫자로 치환**했다. 본문에 나오는 수치는 실제 값이 아니며 본문에서도 예시임을
> 밝힌다. 엔드포인트 경로·내부 함수명은 원본이 "일반적 구조 수준이라 공개 무방"으로
> 분류했으나, 이 글의 논지에 필요하지 않아 쓰지 않았다.

## 핵심 (원본에서 도출)

1. **증상.** 홈 카드가 "정리할 사진 N장"을 표시하는데, 정리 세션을 끝까지 돌려도
   숫자가 그대로였다.
2. **첫 가설 기각.** "완료 후 재조회가 없겠지"를 의심했는데, 세션 종료 핸들러가 **이미
   재조회를 하고 있었다.** 신선도 문제가 아예 아니었다.
3. **두 번째 단서.** 같은 계정인데 **웹은 0장, 모바일은 N장**이었다.
4. **원인은 두 겹이었다.**
   - **(a) 정의 불일치(공급자).** "정리 대상"이라는 같은 개념이 두 코드 경로에서
     다르게 정의돼 있었다. **정리 세션 큐**는 사용자의 *간직/나중에* 신호로 항목을
     제외하는데, **홈 카드의 카운트 API**는 그 신호를 전혀 참조하지 않고 원시
     상태(품질 점수, 중복 그룹 멤버십)만 집계했다. 그래서 사용자가 *간직*을 눌러
     정리를 끝낸 사진이 **큐에서는 사라지지만 카운트에는 계속 잡힌다.**
   - **(b) 스냅샷 고착(소비자).** 오래 살아 있는 네이티브 앱에 "마운트 시 1회만
     페치" 가드가 있어 며칠 전 숫자가 그대로 남아 있었다.
5. **이 글의 논지(한 개).** **신선도만 고쳤다면 "정확하게 틀린 숫자"가 됐을 것이다.**
   두 겹 중 하나만 고치면 증상이 사라지지 않거나, 더 나쁘게는 *갓 가져온 틀린 값*이
   된다.
6. **재발 방지 — 정의를 공유하라.** 화면에 노출되는 집계 숫자는 *무엇을 세는가*의
   정의를 **소비자와 공급자가 공유**해야 한다. 여기서는 **제외 목록이라는 공통 개념이
   이미 존재했는데 통계 쪽만 참조하지 않았다.**
7. **부수 교훈 ①.** 오래 사는 네이티브 앱에서 "마운트 1회 페치" 가드는 **웹의 감각으로
   넣으면 안 된다.** 재진입 에지 + 앱 resume 에지에서 갱신한다(폴링은 넣지 않았다).
8. **부수 교훈 ②.** 완료 화면 내용이 몇 초 뒤에 나타나던 문제는 느린 순차 커밋 뒤에
   통계 페치가 줄 서 있던 것. 라이브 집계형 API는 **"즉시 1회 + 커밋 후 재조회" 이중
   페치**가 체감과 정확성을 동시에 잡는다.
