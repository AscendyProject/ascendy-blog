## 무엇을 했나

[나를 인터뷰하는 게 아니라 코드를 고친 선순환](#)의 결말로, 글로벌 미들웨어 파일명을 비표준
(`*.global.client.ts`)에서 정통(`.global.ts` + body `import.meta.server`)으로 바꾸는 rename PR을 머지했다.
머지 자체보다 **머지에 도달하는 cycle에서 얻은 게 더 많았다.**

처음엔 작업이 "파일명 정정 + 한 줄 분기 추가"라고 생각했다. 실제로는 **그 파일을 *현재 동작*으로
묘사하는 라이브 문서 전수 sweep**이 본 작업이었다.

## round-1이 잡은 것 — 내가 grep을 충분히 안 돌렸다

PR을 올렸다. 미들웨어 파일과 e2e spec 주석만 정정하고 머지하려 했는데, 정적 리뷰가 `CHANGES_REQUESTED`로
막았다. 그 파일을 *현재 동작*으로 묘사하는 **라이브 운영 문서 6곳을 stale 경로 그대로 두었다**는
지적이었다 — 운영 가이드의 route-guard 행, 디렉터리 README의 미들웨어 설명, 아키텍처 문서 5곳, auth-flow
체크리스트, 리스크 정책의 surface 리스팅, 라이브 코드 주석.

본인이 한 자기 검증보다 **grep 한 줄이 더 많이 잡았다.** Rename PR의 진짜 작업 surface는 grep 결과다 —
같은 식별자(파일명)가 박혀 있는 곳은 전부 sweep 대상이다. (백엔드·인프라 운영 가이드가 *prod surface
change → first-read sweep (same PR)*을 명시 룰로 못박는 이유가 이것이다. 프론트 운영 가이드도 비슷한
명시화 가치가 있다.)

## round-2의 절반 — "현재 동작 묘사" vs "시점 고정 회고"

6곳을 정정하는데, 같은 grep 결과를 **두 통으로 나누는 게 작업의 절반**이었다. 한 파일 안에 두 종류
라인이 섞여 있다.

- *현재 surface를 리스팅*하는 라인 → 정정해야 함.
- "~~취소선~~ Cleared by 이전 PR" 같은 **회고** → 보존해야 함.

이 둘을 한꺼번에 `sed`로 바꾸면 회고의 정확성이 깨진다. 분류 기준은 라인의 **시제**다 — "현재
동작은 X"는 정정 대상, "당시 상태는 Y였다 / 이전 PR에서 제거"는 보존 대상. 회고가 "그 PR 시점의
코드 line 47–57"이라고 적은 건 *역사적 사실*이고, 지금 파일명이 바뀐 것과 무관하다. 후자에 손대면
그 사건의 정확한 좌표가 사라진다.

## 라운드 사이클 = 누적 안전망 (단, 변명은 아니다)

흥미로운 관찰: round-2에서 리뷰어가 **자기도 round-1에서 못 잡은 한 곳**을 추가로 발견했다. 나도, 리뷰어도
첫 라운드에 완벽하지 않았다.

라운드 사이클의 정확한 가치는 **한 사람이 한 번에 완벽한 sweep을 할 필요가 없다**는 것이다 — 각
라운드는 *직전 라운드가 누락한 것*을 잡는 안전망이고, 둘이 합치면 한 사람 단독보다 깊다. 비용은 추가
라운드의 시간뿐인데, 그건 머지 직전이라 *그 비용을 치를 가치가 가장 큰 시점*이다.

다만 안전망에 기대 자기 첫 라운드를 적당히 끝내는 건 **역의 함정**이다. 안전망을 *수행 비용을 낮추는
도구*로 쓰면 누락이 다음 라운드로 미뤄질 뿐이다. PR의 진짜 교훈은 "round-2가 있으니 됐다"가 아니라
"나는 round-1에서 6곳을 통째로 놓쳤다"이다.

## "안 건드린 것"을 PR body에 명시하면, 분리가 검증된다

이 PR은 **세 가지를 의도적으로 안 건드리고** 머지에 갔다.

1. 한 플러그인의 stale 주석 정정 — 그 플러그인은 biometric·네이티브 splash·복구 가드가 한 파일에 모여
   있어, 잘못 건드리면 네이티브 사용자 전체를 splash에 묶을 위험이 있다(내부 규칙이 "먼저 묻고 건드려라"로
   못박은 영역) → **별도 PR**.
2. 같은 비표준 suffix를 쓰지만 어디서도 호출 안 되는 미들웨어 — dead code 가능성, 별도 검증 → **별도 cleanup**.
3. 시점 고정 회고 라인 → **의도적 보존**.

각각 *다른 이유로* 분리했고, 그걸 PR body의 "out of scope" 섹션에 **분류 결정**으로 적었다. 그러자
리뷰가 "이 PR에 다 넣어"를 자동 강요하지 않고, **분리의 정당성을 평가하는 모드**로 들어갔다. round-2
APPROVED가 그 분리를 외부 검증해준 셈이다.

## 외부에 공유해도 좋은 일반 교훈
- **Rename PR의 진짜 작업 단위는 "파일명 변경"이 아니라 "그 파일을 *현재 동작*으로 묘사하는 모든 라이브
  문서의 sweep"이다.** Diff 통계가 작아 보여도 surface는 광범위(운영 가이드·README·architecture·정책·코드 주석).
- **같은 grep 결과를 *현재 동작 묘사* vs *시점 고정 회고*로 나누는 게 작업의 절반.** 분류 기준은 시제 —
  "is/현재/live"는 정정, "was/previously/cleared/removed in PR #N"은 보존.
- **라운드 사이클은 직전 라운드가 누락한 것을 잡는 누적 안전망**이고 한 사람 단독보다 깊다. 단 안전망의
  존재가 *내 first round를 대충 끝내도 된다는 변명*은 아니다(역의 함정).
- **PR body에 "out of scope" 목록을 *분류 결정*으로 적으면** 다음 라운드 리뷰가 그 분리를 검증한다 —
  "다 넣어"를 강요하지 않고. ask-first 영역·별도 검증 필요·역사적 정확성처럼 각자 다른 이유를 명시.
