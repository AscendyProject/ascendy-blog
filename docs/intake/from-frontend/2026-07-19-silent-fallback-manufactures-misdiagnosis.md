## 핵심 (원본에서 도출)

1. **증상.** 친구와 주고받은 사진 목록이 계속 비어 보였다. 모바일·웹 동일, 서버는
   **200**, 콘솔 에러 없음, CI 초록불.
2. **진짜 원인.** 응답의 두 버킷은 **직접 배열**인데 코드가 배열의 하위 필드를 읽었다.
   배열엔 그 필드가 없어 `undefined`가 되고, **조용한 빈-배열 폴백(`?? []`)**이 그걸
   빈 배열로 바꿨다. 예외도 타입 에러도 없이 결과가 0건이 된다.
3. **이 글의 논지(한 개).** "조용한 폴백은 버그를 숨긴다"에서 한 걸음 더 나간 것 —
   **신호가 없으면 진단이 그럴듯한 오진을 만들어낸다.**
4. **오진 셋, 그중 둘은 진짜 버그였다.** 가상 스크롤러가 중첩 flex 레이아웃에서 높이 0으로
   렌더되던 문제, 목록 요청이 같은 store를 덮어써 생기던 경쟁 — 둘 다 실재했고 고칠 가치가
   있었지만 **사용자가 본 증상과는 무관**했다. 실재하는 버그를 고쳤다는 사실이 오히려
   "원인을 찾았다"는 착각을 만들었다. (나머지 하나는 배포 지연으로 데이터가 잠깐 비어
   보였던 것.)
5. **돌파구는 실제 Network 응답 body 한 덩어리**였다. 며칠치 삽질이 한 번에 끝났다.
6. **유입 경로 — 크로스레포 계약 desync.** 백엔드의 breaking change *스펙*에 맞춰 프론트가
   **하드 컷오버**했는데, **그 스펙대로의 응답이 실제로 배포된 적이 없었다.**
7. **CI·리뷰가 못 잡은 이유 셋.** (a) 조용한 폴백은 예외를 안 던진다. (b) 테스트 목업이
   코드의 가정을 그대로 복사해 **테스트가 자기 자신을 검증**했다 — 실제 응답 픽스처가
   없었다. (c) 단일 레포 정적 리뷰는 코드가 내부적으로 일관되면 통과시킨다. 이건 코드 결함이
   아니라 **런타임 크로스레포 계약** 문제라 실 백엔드를 치지 않으면 안 보인다.
8. **해법.** 하드 컷오버 대신 **관용 파싱**(알려진 두 shape를 *열거*해 수용) + **실제 응답
   모양으로 behavioral 테스트를 잠금** → 누군가 다시 한쪽으로 하드 컷오버하면 CI가
   빨간불이 된다. **중요**: 관용 파싱이 "알려진 모양이 아니면 조용히 빈 배열"이 되면
   원래 결함을 그대로 재생산한다. 열거에 없는 입력(`null`, 문자열, `{}`,
   `{items: null}` 등)은 **관측 가능한 신호로 표면화**해야 하며, 반환값이 빈 배열이어도
   무방하다 — **문제는 빈 배열이 아니라 침묵이었다.** (블로그팀 검수에서 초안 예제가
   이 조건을 어긴 것이 발견되어 수정함.)
9. **구조적 해법.** 단일 스키마에서 양쪽 타입을 생성하는 공유 API 계약. 각자 손으로 타입을
   정의하는 한 shape drift는 계속 난다.
