## 무엇을 했나

구현 에이전트와 리뷰 에이전트(다른 모델) 페어로 코드를 굴리는 사내 하니스가 있다. 기존엔 리뷰어를
별도 터미널 멀티플렉서 세션으로 띄워, 사람이 프롬프트를 복붙하고 sentinel 파일로 결과를 받는
**수동 중계** 구조였다. 이게 가장 큰 마찰이었다.

리뷰어 CLI가 **headless(non-interactive) 모드**를 지원하는 걸 확인하고, 리뷰를 화면 제어가 아니라
**subprocess 호출**로 바꿨다: 프롬프트를 stdin으로 주고, "마지막 줄에 `REVIEW_DECISION: APPROVED|
CHANGES_REQUESTED` + 발견 항목을 ID로" 형식을 강제해 stdout을 기계 파싱한다. 화면 파싱(ghost
텍스트·타이밍·포커스 인시던트), 별도 세션, sentinel 중계가 통째로 사라졌다.

그 루프로 이번 변경들을 실제로 리뷰했다 — 설계 문서 1편 + 코드 PR 2건. 결과가 글감을 만든다.

**(1) 설계 문서 리뷰는 수렴했다.** 같은 문서를 4라운드 돌렸더니 `CHANGES_REQUESTED` 항목이
**9 → 7 → 3 → APPROVED**, 토큰도 단조 감소. 핵심은 3라운드에서 리뷰어가 **"이건 설계 문서이고 필드
단위 명세는 구현 PR에서 정한다"는 사람이 그은 경계를 명시적으로 받아들이고** 더 깊은 명세를
재요구하지 않은 점이다. adversarial 리뷰는 방치하면 끝없이 더 깊은 디테일을 요구한다 — **멈춤선은
사람이 긋고, 리뷰어가 그 선의 정당성을 판정**하게 하는 게 수렴의 열쇠였다.

**(2) 코드 리뷰는 진짜 결함을 잡았다.** 한 PR(신규 API 엔드포인트)을 "단순하니까"라며 리뷰 게이트
없이 올렸는데, 헤드리스 리뷰가 단계적으로 (a) 계층 경계 위반(라우터가 인프라 클라이언트 직접 호출),
(b) 비원자적 레이트리밋(크래시 시 영구 차단 가능), (c) 외부 API의 4xx/5xx를 성공으로 삼킴,
(d) **시크릿이 에러 로그로 새어나갈 뻔한 것**(발견 즉시 같은 PR에서 수정)을 잡았다. 다른 PR(리팩터)
에선 (e) 중앙화에서 빠뜨린 모델 식별자 하나와, (f) "하드코딩 금지" 가드 테스트가 **큰따옴표만
검사하는 허점**을 리뷰어가 **직접 재현**해서 보여줬다(작은따옴표면 통과). 가드를 AST 기반으로 고쳤다.

## 왜 했나 — 두 가지 본질

첫째, **"두 번째 에이전트를 어떻게 부르는가"가 자동화의 성패를 가른다.** 직관적으론 "화면을 완벽히
제어한다"지만, 화면 파싱은 본질적으로 취약하다. 결과를 **stdout/파일**로 받는 subprocess 모델로
바꾸자 취약점이 통째로 사라지고, 부수적으로 "리뷰어를 별도 세션으로 띄울 필요"조차 없어졌다.
협업 상대(다른 레포의 살아있는 에이전트)와 **리뷰 함수(같은 작업을 검토하는 stateless 호출)**는
다른 것이고, 후자만 headless로 보내야 한다는 경계도 분명해졌다.

둘째, **adversarial AI 리뷰는 수렴하지만 점근적이다.** 무한정 돌리면 리뷰어는 계속 더 깊은 명세를
요구한다. "ideation은 방향, 구현 PR은 명세"라는 경계를 사람이 긋고 리뷰어가 그 경계를 판정하게 하니
4라운드에서 깨끗이 APPROVED로 끝났다. 그리고 리뷰가 잡은 결함들(계층 위반, 시크릿 로그 노출,
quote-only 가드)은 사람 리뷰가 놓치기 쉬운 종류였다 — "단순해 보이는 변경"일수록 리뷰 게이트를
건너뛴 대가가 크다는 걸 데이터로 확인했다.

## 외부에 공유해도 좋은 일반 교훈
- 두 번째 AI 에이전트를 **화면 제어가 아니라 headless subprocess + 구조화 출력(REVIEW_DECISION/
  finding-id)**으로 호출하는 패턴, 결과를 파일/stdout으로 받는 게 화면 파싱보다 견고하다는 일반 교훈.
- **adversarial AI 리뷰의 수렴 곡선**(라운드마다 항목 수·토큰 감소)과, "ideation vs 구현 명세" 경계를
  사람이 긋고 리뷰어가 판정하게 해 무한 정밀화를 끊는 패턴.
- "단순해 보이는 변경"을 리뷰 게이트 없이 올렸을 때 자동 리뷰가 잡은 결함 **유형**(계층 경계 위반,
  비원자적 카운터의 영구 차단, 외부 API 실패를 성공으로 삼킴, 시크릿이 에러 로그로 누출, quote-only
  정적검사 허점)과 일반 교훈.
- 리뷰어가 자기 지적을 **직접 재현해 증명**하는 행동의 가치(가드 우회를 코드로 보여줌).
- read-only 샌드박스 리뷰어는 테스트를 못 돌릴 수 있으니 테스트는 별도로 돌려야 한다는 운영 팁.
