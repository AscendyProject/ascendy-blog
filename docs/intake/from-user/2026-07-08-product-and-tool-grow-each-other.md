> 인터뷰(/interview)로 도출. **메커니즘 수준으로만 서술** — 특정 이슈 번호를 박지 않음.
> 이유: '어느 제품 불편이 어느 레드팀 이슈가 됐나'라는 세부 출처는 운영자가 아니라
> 이슈를 올린 에이전트들에게 분산돼 있어(운영자 본인 증언), 운영자 1차 지식으로 특정
> 이슈를 교차-레포 발원이라 단정하면 fabrication이 됨. 그 '출처가 나한테도 없다'는
> 사실 자체가 글의 인사이트. **redaction:** 어센디는 '내가 만드는 제품' 수준으로만
> (제품 내부·기능·전략 노출 금지). 레드팀은 공개 오픈소스라 언급 가능. 클러스터·시크릿·
> 사내 호스트 없음. **1인칭 라벨:** 이 조직 설계는 운영자 방식이지 정답 주장 아님.

## 핵심 (인터뷰에서 도출)

1. **두 개의 루프.** loop engineering = 하네스 *안*의 검증 루프(AI가 도는 것).
   이 글 = 하네스 *밖*, 사람이 설계한 *조직*이 도는 루프(내가 도는 것). "큰 의미의 루프."
2. **한 바퀴의 구조.** 백엔드/프론트 에이전트가 레드팀으로 제품을 구현 → 쓰다가 "이건
   하네스 문제 같다" 보고 → 운영자가 "레드팀 레포에 이슈 등록" 라우팅 → 레드팀 담당
   에이전트가 이슈 타당성 검토 → 실제 문제면 dogfooding으로 개선 → 나아진 도구가 다음
   제품 작업을 낫게 함.
3. **왜 인라인이 아니라 이슈인가.** 기록이 남아야 세션이 리셋돼도 "그거 읽어봐"로 복원됨.
   기록의 1차 독자는 사람이 아니라 리셋된 다음 세션의 에이전트. 원래 docs로 깃헙에
   누적하다가 "좋은 툴(이슈 트래커)을 그냥 쓰면 된다"로 이동.
4. **왜 게이트를 에이전트에게.** 처음부터. 각 에이전트에 (a) 전체 프로젝트 컨텍스트 (b) 자기
   역할 (c) 다른 담당 에이전트가 존재한다는 사실까지 심음 → 서로의 역할을 알아 라우팅이
   그냥 됨. 게이트를 사람 아닌 도구-담당 에이전트에 둔 건 이 조직 설계의 일부.
5. **헛돌지 않는 이유(선순환인 근거).** 병렬이라 도구 고치는 동안 제품 만드는 에이전트는
   멈추지 않음 + 타당성 게이트가 헛짓(yak-shaving)을 거름.
6. **사람의 자리는 위로.** 세부 출처(provenance)조차 운영자한테 없고 에이전트들에게 분산됨.
   운영자는 설계·라우팅 층에만 있음 — 위임을 극한까지 밀어올린 결과.

## 연결

- 검증이 loop engineering의 핵심([loop-engineering-verifier]), 조율은 파일 아닌 이슈로
  ([coordination-context-pollution]), 위임은 붙잡는 지점을 옮기는 것
  ([i-didnt-design-it-i-delegated])과 같은 결. 이 글은 그 위의 제품↔도구 공진화가 중심.

## 외부 공유 불가

- 어센디 제품 내부·기능·전략(일반화, '내가 만드는 제품' 수준). 특정 레드팀 이슈 번호를
  교차-레포 발원으로 단정(금지 — 출처 미확인). 클러스터·시크릿·사내 호스트 없음. 레드팀은
  공개 오픈소스.
