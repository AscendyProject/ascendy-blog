> 사내 하네스 디테일은 일반화하고 redteam(공개 OSS, Apache-2.0)만 구체. 모델명(GPT/Claude/
> Gemini/Codex)은 협업 주체(공개 범위). **fact:** 젠스파크 모델 교차검증은 web 검증(MoA 구조로
> orchestrator가 best 모델 라우팅 + mutual verification 교차 체크) — 미검증 제품/런칭 세부는
> 제외하고 교차검증 구조만 인용. 시크릿 없음.

## 핵심 (인터뷰에서 도출)

1. **앵커 에피소드.** 누가 "병렬로 일 시킬 때 깃헙 브랜치가 안 꼬이게 어떻게 *설계*했냐"고 물었다.
   답: **"설계 안 했다. 에이전트에게 맡겼다."** task만 던지고 task 간 의존성·순서·병렬 가능 여부를
   에이전트가 판단하도록 하네스를 구성. 질문자 반응: "아, 그런 것도 다 맡기는구나."
2. **개발자 본능이 장애물.** 개발자는 평생 "이걸 *내가* 어떻게 풀지, 어떤 기술 쓰지"로 훈련됨.
   바뀌어야 할 질문: "이걸 어떻게 *맡기지*? 맡긴 결과를 어떻게 *신뢰하게 만들지*?"
3. **함정.** "복잡하니까 내가 해야지 / 할루시네이션하니까 내가 봐야지"는 합리적으로 들리지만
   거기서 멈추면 **인간이 병목.** (운영자 경험: 프롬프트 개선+직접 확인으로 풀다 시간·노동 효율
   개선 안 됨 — 내 손이 천장.)
4. **전환.** "내가 봐야지"가 아니라 "어떻게 *안 보고도* 믿지" → 하네스 + 루프 엔지니어링. 검증을
   *내가 하는 일*에서 *구조가 하는 일*로. redteam 하네스 + 루프 + dogfooding으로 신뢰 도구로
   발전 → 지금은 결과만 확인+피드백, 대부분 위임.
5. **신뢰 구조 핵심 = 모델 교차 검증.** 한 모델이 아니라 다른 계열 모델의 교차 검증. 젠스파크가
   이를 MoA로 서비스화(web 검증). 단 모델 2개+ 구독 중이면 redteam류 하네스로 직접 교차검증 가능.
6. **균형.** 다 맡기는 게 아니다. 끝까지 사람이 쥐는 건 *무엇을 맡길지 정하고, 결과를 판단하고,
   피드백하는 것.* 위임 = "손 떼기"가 아니라 *통제점을 옮기는 것.*
