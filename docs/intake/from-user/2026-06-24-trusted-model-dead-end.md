> 운영자가 직접 겪은 인프라 마이그레이션 일화. **전부 실제 사건**이며 가상의 예시가 아니다.
> **톤 가드레일(편집 시 준수):** ① Claude를 깎아내리지 않는다 — 메시지는 "Claude가 틀렸다"가
> 아니라 "어떤 단일 모델도 자기 시야 밖을 못 본다"는 *구조적 사실*이다(마지막 구현도 다시
> Claude가 했다 = 버린 게 아니라 교차시킴). ② 시간("1년 걸렸다")을 자랑하지 않는다 — 시간은
> 맥락일 뿐, 보여줄 것은 *판단과 사건*. ③ 정직성 최우선 — 확신 없는 수치는 단정하지 말고
> 검증 게이트에 맡긴다. **A안 원칙:** CTA는 redteam GitHub repo 하나뿐, Ascendy 유도 금지.
> **Class A/B 없음** — 인프라 스택명(VKE/RunPod/Triton/vLLM 등)은 ai-serving 시리즈에서 이미
> 공개된 벤더·제품명이고, 시크릿·클러스터명·실IP는 없다.

## 실제로 일어난 4단계 (순서 유지)

1. **Gemini API 직접 호출** — 사진 전처리를 Gemini API로 시작. 몇백 장은 됐지만 수천·수만 장
   스케일에서 비용 구조가 깨져 서비스 자체가 성립 불가. → *한 모델의 가장 쉬운 답이 스케일에서
   깨지는 지점.*
2. **VKE GPU 노드 (Claude 추천)** — 직접 GPU로 처리하고 싶다고 하자 Claude가 VKE GPU 노드를
   추천. 신뢰하고 그대로 감. 결과: 쪼개 쓰는 비효율 GPU, 비싼 비용, 끝없는 OOM. 유저도 없는데
   고가 GPU 노드를 상시로 돌리는 것도 과했다. 그리고 Claude는 *자기가 추천한 구조 안에서만*
   맴돌 뿐 그 바깥을 보여주지 못했다. → ★*가장 신뢰한 모델이 자기 시야 밖을 못 보는 지점(글의
   심장).*
3. **RunPod 24/7 (GPT·Gemini 제시)** — 막혀서 GPT·Gemini에게 같은 고민을 전달. 둘이 RunPod이라는,
   그때까지 사고 범위에 없던 축을 제시. 24/7로 돌리니 수천 장 동기화 처리됐고 OOM도 사라짐.
   → *다른 계열 모델이 시야를 메우는 지점.*
4. **서버리스 전환 (Gemini 방향 + Claude 구현)** — 안 쓸 때도 나가는 비용이 아까워 다시 물으니
   Gemini가 서버리스로 바꾸라 함. 그 방향을 Claude에게 들고 가 구현. 운영비 급감. → *방향과
   구현이 서로 다른 모델에서 나오는 지점.*

## 핵심 통찰

> 정답은 어느 한 모델 안에 없었다. 모델 사이를 오가는 과정에 있었다.

이 과정을 매번 손으로 하는 게 지쳐서 — 그리고 매번 같은 종류의 가치를 줬기 때문에 — 자동화한
것이 **redteam**(멀티모델 교차검증 하네스)이다. 도구가 먼저 있고 사례를 갖다 붙인 게 아니라,
사례가 먼저 있고 그것이 도구를 낳았다.

redteam의 모델 독립적 원칙 셋: ① 코드를 짠 모델이 그 코드의 안전성을 스스로 판단하면 안 된다
② 리뷰어는 작성자와 다른 계열이어야 동조(rubber-stamp)를 깬다 ③ 최종 머지는 항상 사람.

## 연결

- 같은 인프라 여정의 *결과물* 관점은 ai-serving 시리즈(part1/part2)에 이미 발행됨 — 이 글은
  그 결정에 *어떻게 도달했는가*(멀티모델 측면)에 집중하고 cross-link한다.
- redteam을 루프 엔지니어링 관점에서 본 글(loop-engineering-verifier)과 같은 결.

## 외부 공유 불가

- 없음(인프라 스택명은 기존 공개 범위, 시크릿·클러스터명 없음). 비용 액수는 글에서 단정하지
  않는다(정성적 서술만).
