# 서비스 블로그 운영 규약 (`/stories/`)

이 문서는 **Ascendy 서비스 블로그**를 운영하는 세션의 구속력 있는 규약이다.
기술 블로그(`/blog/`)를 지배하는 [`editorial-policy.md`](./editorial-policy.md)와
**병렬로 존재**하며, `/stories/` 경로의 글에는 이 문서가 우선한다.

서비스 블로그 작업은 **기술 블로그와 다른 세션에서** 한다. 저장소·배포·리뷰
파이프라인은 공유하되 세션은 분리한다 — 독자와 목소리가 다르고, 72편치 엔지니어링
맥락을 이고 쓰면 프레이밍이 그쪽으로 끌린다.

---

## 1. 목적

단순 홍보 블로그가 아니다. 만들려는 것은 **성장 루프**다.

```text
제품 사용 → 실제 문제 발견 → 제품 개선 → 그 과정을 콘텐츠화
   → 검색·SNS·AI 답변엔진 유입 → 신규 사용자 → 피드백 → 다시 제품 개선
```

성공은 글 수가 아니라 이 루프가 도는지로 판단한다.

## 2. 포지셔닝

Ascendy를 **사진을 저장하는 장소를 하나 더 만드는 것**으로 표현하지 않는다.
다루는 문제는 **이미 가지고 있는 추억을 다시 찾고 활용하지 못하는 것**이다.

구체적으로: 수년간 쌓인 사진을 다시 찾기 어려움 / 여러 기기·서비스에 흩어짐 /
직접 앨범·폴더로 정리하는 번거로움 / 비슷하거나 중복된 사진 / 가족과 공유의 불편 /
아이 사진을 SNS에 올리고 싶지 않음 / 사진은 많은데 과거를 다시 발견하기 어려움.

## 3. 독자 — 기술 블로그와 절대 혼동하지 않는다

| | 기술 블로그 `/blog/` | 서비스 블로그 `/stories/` |
|---|---|---|
| 독자 | 개발자·AI/클라우드 엔지니어·기술 창업자 | 사진을 많이 찍는 사람, 부모, 가족, 사진 관리에 어려움을 겪는 사람 |
| 화자 | "우리" (팀) | **"나" (창업자 1인칭)** |
| 무게중심 | 구현·결정·트레이드오프 | **사용자의 문제와 경험** |
| 기술 용어 | 실명 그대로 | 일반인이 이해할 수준으로만 |

기술은 **사용자가 느끼는 결과**로 번역해서 쓴다.

- ❌ "coarse-to-fine 검색을 Matryoshka 임베딩으로 구현했다"
- ✅ "사진이 늘면서 검색이 느려져서, 후보를 좁히는 방식을 바꿨다"

## 4. 카테고리 (스키마 enum과 1:1)

- **`real-stories`** — 실제 사진 관리 경험
- **`building`** — Build in Public. changelog가 아니다. 항상 이 순서:
  *문제 → 실제 사용 중 발견 → 왜 불편했나 → 어떤 결정을 했나 → 무엇을 바꿨나 → 지금 어떤가*
- **`guides`** — 사진 관리 정보성 콘텐츠(검색 유입). 실제로 도움이 되는 내용을 먼저
  주고, **그 문제를 Ascendy가 해결할 수 있을 때만** 자연스럽게 연결한다
- **`philosophy`** — 왜 이 제품을 만드는가

## 5. ⚠️ 날조 방지 — 이 블로그의 최대 위험

기술 블로그의 최대 위험이 시크릿 누출이라면, **서비스 블로그의 최대 위험은 없는
경험을 지어내는 것**이다. 1차 소스가 창업자의 기억에만 있고 콘텐츠의 본체가 1인칭
경험이라, 구조적으로 날조 위험이 훨씬 높다.

**"모르면 물어본다"는 규칙만으로는 지켜지지 않는다.** 글을 쓰라는 지시를 받은
에이전트는 빈칸을 그럴듯하게 메운다. 그래서 두 겹으로 강제한다.

### (a) 스키마 게이트 — 빌드 실패

`real-stories` · `building` · `philosophy` 는 **`sourceIntake`가 필수**다
(`src/content.config.ts`의 refine). 근거 파일 없이는 **빌드가 실패한다.**
`guides`만 면제.

### (b) 인터뷰가 유일한 1인칭 입구

창업자 경험이 필요한 글은 **초안을 쓰기 전에 인터뷰를 돌린다**(`/interview`).
장면·숫자·감정을 **실제로 말하게 하고**, 인터뷰에서 나오지 않은 디테일은 쓰지 않는다.
정제본은 `docs/intake/from-user/`에 두고 `sourceIntake`가 그것을 가리킨다.

절대 지어내지 않는 것: 사용자 후기, 사용자 수, 성장·매출 수치, 개인 경험, 보유 사진
수량. 모르면 **모른다고 처리한다.**

## 6. 공개 경계 (redaction)

기술 블로그의 [`redaction-checklist.md`](./redaction-checklist.md)를 승계하되,
서비스 블로그는 **사업·사용자 축**이 추가된다.

**절대 쓰지 않는다**

- **사용자 피드백 인용** — 동의 없는 인용은 사고다. 익명화해도 원문 인용은 금지.
  "이런 요청이 반복해서 들어왔다" 수준의 **요약**만 가능
- 사용자 수, 가입자 수, 업로드량, 매출·성장 수치 (공개 결정 전)
- 개인 사진의 내용 묘사, 가족·지인의 식별 가능한 정보
- 미발표 로드맵, 미출시 기능을 있는 것처럼

**주의해서 쓴다**

- **경쟁 서비스** — 부당하게 깎아내리거나 사실을 왜곡하지 않는다. 확인 가능한 동작만
  쓰고, 그 서비스가 그 선택을 한 이유를 함부로 추측하지 않는다
- **아직 불확실한 기능** — 제품에 실제로 있는지 확인한 뒤 쓴다
- **미수정 결함** — 기술 블로그와 동일하게 Class A. 고쳐서 배포된 뒤에만 쓴다

## 7. 문체 — 마케팅 블로그처럼 쓰지 않는다

남발 금지: *We are thrilled to announce, Revolutionary, Game-changing,
Best-in-class, Cutting-edge, Seamless, Ultimate solution.*

**제품을 무조건 칭찬하지 않는다.** 부족한 점, 실패한 시도, 불편했던 부분을 필요하면
공개한다. 이런 문장이 오히려 좋다:

> 설계한 대로 동작하긴 했는데, 일주일 써보고 나서 설계 자체가 틀렸다는 걸 알았다.

독자가 느껴야 하는 것은 *"이 회사가 자기 제품을 광고하네"*가 아니라
*"이 사람이 실제로 이 문제를 겪으면서 만들고 있구나"*다.

## 8. 제목

제품 이름이 아니라 **문제·경험**으로 시작한다.

| 나쁨 | 좋음 |
|---|---|
| Ascendy가 AI 검색을 개선했습니다 | 원하는 사진은 찾았는데, 똑같은 사진 20장이 같이 나왔다 |
| Ascendy 사진 정리 | 가족 사진을 폴더로 정리하는 걸 그만둔 이유 |

단, **비교 검색 수요가 목적이면** 비교형 제목을 쓸 수 있다.

## 9. 제품 언급과 CTA

콘텐츠 자체가 먼저 가치 있어야 한다. 억지로 팔지 않는다.

- ✅ "그래서 Ascendy에 자연어 검색을 넣었다."
- ❌ "Ascendy는 최고의 사진 관리 솔루션입니다. 지금 가입하세요!"

CTA가 필요하면 최대한 자연스럽게. 제품 링크 정도면 충분하다.

## 10. 언어 — ko 원문, en 필수

**한국어로 원문을 쓰고 영어 판을 반드시 함께 낸다.** 1차 타깃 시장이 북미이므로
en은 선택이 아니다. `translationKey`로 짝짓고, hreflang은 자동으로 붙는다.

영어는 원어민 마케팅 카피처럼 꾸미지 않는다. **짧고 명확하고 개인적인 문체**로,
창업자의 실제 생각이 느껴지게. `description`은 ko/en 모두 **220자 상한**이고
en이 같은 내용에 약 1.8배를 쓰므로 특히 주의한다.

## 11. 소재 발굴 (Build in Public)

최근 제품 변경에서 소재를 찾되, **기술 변경 자체가 아니라 "왜 이걸 고쳤는가"**를
소재로 판단한다.

- 기술 변경: 유사도 클러스터링 알고리즘 변경
- 서비스 소재: **검색 결과에서 비슷한 사진을 전부 보여주는 걸 그만둔 이유**

찾을 것: 최근 추가 기능 / 고친 버그 / 검색 품질 개선 / UI 변경 / 업로드·정리·중복·
공유·프라이버시 관련 변경 / **창업자가 직접 쓰다 발견한 문제** / 예상과 실제가 달랐던 기능.

단, 제품 저장소의 raw 정보는 §6의 경계를 통과한 뒤에만 글에 들어온다.

## 12. 아이디어 평가 (5개 이상 만족할 때만 착수)

1. 실제 사용자가 겪는 문제인가
2. 제목만 보고 상황이 이해되는가
3. **Ascendy를 몰라도 읽을 가치가 있는가**
4. 개인적 경험 또는 구체적 관찰이 들어가는가
5. 다른 회사 블로그가 쉽게 복제할 수 없는가
6. 검색하거나 공유할 이유가 있는가
7. Ascendy와 자연스럽게 연결되는가

## 13. SEO / AI 답변엔진

SEO를 위해 품질을 희생하지 않는다. 키워드를 억지로 반복하지 않는다.
글마다 primary intent 1개 + secondary 2~4개를 설계하고, **질문과 답이 명확히
드러나는 구조**를 선호한다(AI 답변엔진이 인용하기 좋다).

## 14. 콘텐츠 재활용

글 하나를 쓴 뒤 채널별 재활용안을 함께 제안하되 **복붙하지 않는다.**

- **X** — 핵심 깨달음 + Before/After
- **LinkedIn** — 제품 결정 또는 창업 관점
- **리멤버** — 한국어 경어체

**⚠️ Reddit은 별도 판단이 필요하다.** 계정 이력 없이 자기 제품 글을 올리면 자기홍보로
분류돼 밴당하고 브랜드가 상한다. **먼저 참여해서 이력을 쌓기 전에는 권하지 않는다.**
[`social-intro`](../.claude/commands/) 관례와 동일하게, 게시는 사용자가 한다.

## 15. 작업 순서

1. 최근 제품 변경·피드백·기존 콘텐츠 확인
2. 후보 발굴 → §12로 평가
3. **1인칭 소재가 필요하면 인터뷰 먼저**(`/interview`) → 정제본을 `docs/intake/from-user/`에
4. 사실 검증 (제품에 실제로 있는 기능인지, 경쟁사 주장이 정확한지)
5. ko 원문 작성 → en 판 작성
6. **마케팅처럼 느껴지는 문장 제거**
7. §6 공개 경계 통과 확인 → `redactionReviewed: true`
8. 검증: `pnpm check` · `pnpm build` · 별표 렌더 누출 · 링크 대상 존재
9. `/redteam:review` (서비스 블로그 하드 라인 적용)
10. PR → 사용자 머지. 첨부하면 좋을 화면·GIF와 채널 재활용안을 함께 제안

## 16. 자율성

스스로 판단한다: 제목, 구조, 소제목, 키워드, 문체, CTA 위치, 내부 링크, 이미지 배치,
재활용 방식.

**반드시 확인한다**: 창업자의 실제 경험을 1인칭으로 쓸 때(→ 인터뷰), 미공개 사용자
수·매출·성장 데이터, 사용자 개인정보, 실제 사용자 후기, 제품에 있는지 불확실한 기능,
경쟁사에 대한 중요한 사실 주장.

## 17. 기술 블로그와 공유하는 것 / 갈리는 것

**공유** — 저장소·배포, 인테이크→정제본→`sourceIntake` 파이프라인, `/redteam:review`
크로스-모델 검수, 발행 전 검증 그렙, `draft: true`는 `main`에 머지 금지, PR + 사용자 머지.

**갈림** — 세션, 독자, 화자(우리 vs 나), 라우트(`/blog/` vs `/stories/`), RSS 피드,
카테고리 enum, 리뷰 체크리스트, 그리고 위 §5·§6의 하드 라인.
